# P1c-1 Accounts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Accounts as the PRD and the locked design describe them:
- **Continue with Google** (Firebase Auth, as in ddinter2);
- guest → account with everything attached;
- "Save your progress" at the end of the first loop, with "Not now" → ScreenGuestNotNow;
- the 3-guest-talk limit (ScreenGuestLimit);
- "I already have an account" → restore, including the Day 1 clip, and skip onboarding;
- closed-beta invite links;
- a `/privacy` page.

**Architecture:**
- **Identity:** `learner` gains an outbound `IdentityPort`, which verifies a Firebase ID token (`FirebaseIdTokens`, nimbus-jose-jwt against Google's securetoken JWKS, iss/aud = the project ID, no service account) and has a `fake` vendor for tests.
- **Sign-in:** `POST /api/auth/google` turns the cookie's guest into an account, or signs into an existing one. A guest's data is merged into an existing account by moving rows: each module listens for `LearnerMerged` and moves its own rows.
- **Firebase web config:** read from server settings at runtime (`GET /api/auth/config`). Sign-in switches on when the box has the four values, with no rebuild.
- **The web** loads the Firebase SDK lazily and uses `signInWithPopup` (desktop beta). It then posts the ID token.

**Tech Stack:** as before, plus `com.nimbusds:nimbus-jose-jwt:10.10` (api) and `firebase@11.1.0` (web; the version ddinter2 runs).

**Spec:**
- `Bolo-PRD-MVP.md`: ACC-1, ACC-2, ACC-7, ONB-4, PRG-7, US-6.8, US-8.1, US-8.2, US-8.4.
- `design/design-system/4-screen-recipes.md`: "End of first loop" and "Account".
- The prototype screens `save`, `start` ("I already have an account").
- The founder's decisions of 2026-11-09: Firebase, PRD guest flow plus invite links, no captcha.

## Global Constraints
- **Sign-in is Google only.** There's no "Use phone number" button: it arrives with phone OTP at public launch and isn't shown in the beta. Google's button keeps Google's colours, and screens with it have no mustard button (design).
- **The first "Continue with Google" creates the account.** There's no separate sign-up. Guest data attaches with no extra step, and the 13+ confirmation and consent carry over (US-8.1).
- **Guests get 3 talks.** A talk counts once its socket attached. Before the 4th, the learner must sign in (ScreenGuestLimit says progress will be kept). The save prompt reappears once after the 2nd and 3rd guest talks (US-8.2).
- **End of the first loop** (US-6.8, PRG-7): the last debrief card offers **Practise (3 min)** (primary: practice on the debrief's first sound, else the sounds list) and **Later**, then **Save your progress** (guests only), then Home with "See you tomorrow".
  - The reminder step waits for Phase 1c reminders and isn't shown.
  - Steps the learner missed are shown once, on the next visit, before Home.
- **Tokens:** an ID token is accepted only if
  - its signature checks against Google's securetoken keys,
  - `iss` = `https://securetoken.google.com/<projectId>` and `aud` = projectId,
  - it hasn't expired,
  - `auth_time` is within the last 5 minutes,
  - `email_verified` is true,
  - and `sub` is non-empty.
  - Otherwise: 401 `{"code":"sign-in-failed"}`.
- **Sign-in off:** when the four `BOLO_FIREBASE_*` values aren't set, `GET /api/auth/config` → `{"enabled":false}`, and the web shows no Google button. Learners stay guests, and the 4th-talk limit is lifted then (a gate nobody can pass would lock everyone out).
- **Invites:** when `bolo.beta.invites-required=true` (production), a new guest (`POST /api/session`) or a new account (Google, with no guest and no existing account) needs a valid invite code.
  - Codes come from `scripts/invite.sh <label> <max-uses>`, which prints `https://bolo.eliooo.org/?invite=CODE`.
  - Existing sessions and accounts are never gated.
  - A missing or used-up invite gives 403 `{"code":"invite"}`, and the web shows "Bolo is in a closed beta. Ask for an invite link."
- **Cookies:** sign-in rotates the session cookie (a new token for the account; the guest's token is deleted). Sign-out deletes the session and clears the cookie.
- **The Day 1 clip** is uploaded after sign-in only if the learner chose to keep recordings (ONB-4). It's stored encrypted as `learner/<id>/day1.wav`, at most 60 s of 16 kHz mono WAV, and downloaded into IndexedDB on restore.

## Review Focus
1. A guest signs into an **existing** account on a new browser after 2 guest talks: the talks and their debriefs now belong to the account, and nothing is left on the deleted guest. Test: Task 2.
2. A token for another Firebase project, an expired one, an old `auth_time`, or `email_verified=false` → 401, and no learner is created. Test: Task 1.
3. Double-clicking "Continue with Google", so two posts race: one account, not two (unique `firebase_uid`, and the second post signs in). Test: Task 2.
4. A guest who has done 3 talks and never signed in can't start a 4th through the API (not only in the UI), while sign-in is enabled. Test: Task 3.
5. An invite link used up by its last use: the next new guest is refused, but a returning learner with a cookie isn't. Test: Task 4.

### Task 2: Sign-in, sign-out, and guest → account (api)

  - `learner/application/port/in/SignInUseCase.java`, `learner/application/service/SignInService.java`;
  - `learner/adapter/in/web/AuthController.java`;
  - `common/event/LearnerMerged.java` (record `(LearnerId from, LearnerId to)`);
  - a merge listener in each module that owns learner rows: `talk` (`talk_session.learner_id`), `assessment` (`attempt`), `analytics` (`event`) and `learner` (consent ledger: keep the account's; the profile and settings move only if the account has none).
- Modify: `LearnerView` (+ `AccountView account` = `{email, name}`, or null for guests); `/api/me`.
- Test: `learner/SignInAcceptanceTest.java` (the fake identity vendor).

**Interfaces:**
- `POST /api/auth/google {idToken, invite?}` → 200 LearnerView with a fresh `Set-Cookie`. Cases:
  1. The uid already has an account → sign in. If the cookie was a different guest, publish `LearnerMerged(guest → account)`, then delete the guest.
  2. No account and the cookie is a guest → convert it: `learner.kind = account` plus an `account` row.
  3. No account and no cookie → a new account learner. It needs an invite when invites are required. Consent isn't set yet, so onboarding continues at consent.
- `POST /api/auth/sign-out` → 204 and clears the cookie.
